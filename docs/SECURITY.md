# AgentMeter security: secrets, rotation and the access model

This page says where every secret lives, how to replace one (rotate it), and why AgentMeter is
built the way it is. Commands use the Supabase CLI from the repository folder (PowerShell or bash).

## 1. Rotate now if a secret was ever shared

A password or secret that appeared in a chat, an e-mail, a screenshot or a commit is no longer
secret. Replace it; the old value then stops working.

| What | Where it is used | How to rotate | Who notices |
|---|---|---|---|
| **An admin's password** | Logging in | Log in as that admin → **Profile → Change password**. Or another admin: **Admin → Users → Reset password** (the user must set a new one at the next login). | Their other devices are logged out. |
| **`CLOUD_PREP_SECRET`** | Control plane ↔ cloud preparation service (signed jobs) | Make a new value (below), then set it in **both** places: `npx supabase secrets set CLOUD_PREP_SECRET=<new>` and redeploy the preparation service with the same value (`CLOUD_PREP_SECRET=<new> bash scripts/deploy_cloudprep.sh`, or `scripts/deploy_cloudprep.ps1`). | Nobody; a preparation running at that moment fails and is retried. |
| **`ACCESS_TOKEN_SECRET`** | Signs the short-lived login tokens | `npx supabase secrets set ACCESS_TOKEN_SECRET=<new>` | Everyone is asked to log in again. |
| **`RUN_TOKEN_SECRET`** | Control plane → GPU backend (5-minute, single-use run tokens) | Set the new value in Supabase **and** as `AGENTMETER_RUN_TOKEN_SECRET` on the GPU backend; restart the backend. | Nothing, if both change together. |
| **`BACKEND_SECRET`** | GPU backend → control plane (signed heartbeats and uploads) | Set the new value in Supabase **and** as `AGENTMETER_BACKEND_SECRET` on the GPU backend; restart the backend. | The GPU shows offline until both match. |
| **`TELEGRAM_BOT_TOKEN`** | Run notices and "result moved" alerts | In Telegram, @BotFather → `/revoke` → new token; `npx supabase secrets set TELEGRAM_BOT_TOKEN=<new>` | Nothing. |
| **`HF_TOKEN`** | GPU backend: downloading gated models | huggingface.co → Settings → Access Tokens → revoke and create; set it in the backend's `.env`; restart. | Nothing. |
| **`VAST_API_KEY`** | GPU backend: the idle auto-destroy guard | vast.ai → Account → API keys → revoke and create; set it in the backend's `.env`; restart. | Nothing. |
| **Supabase `service_role` key** | Never used by AgentMeter's code; it bypasses every database rule | Supabase dashboard → Project Settings → API → roll the key. Never paste it anywhere. | Nothing in AgentMeter. |
| **`PASSWORD_PEPPER`** | Mixed into every stored password hash | **Do not rotate** unless it leaked: every password then stops working. If it leaked, set a new one, then reset every user's password from Admin (and the first admin with `scripts/bootstrap-admin.mjs`). | Everyone must get a new password. |

**A new random value** (use one per secret, never reuse):

```bash
openssl rand -hex 32
```
```powershell
# PowerShell (not Command Prompt: type `powershell` first if the prompt does not start with PS)
$b = New-Object byte[] 32; [System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
-join ($b | ForEach-Object { $_.ToString('x2') })
```

Check what is set (values are never shown): `npx supabase secrets list`.

## 2. The access model

- **Database.** Every table has row-level security on and **no policies**, and the public
  `anon` / `authenticated` roles have no grants. Only the Edge Function (its own database role)
  reads or writes; a leaked public API key cannot read a row. Supabase's security advisor reports
  this as "RLS enabled, no policy" (level INFO): that is the intended, strictest setting.
- **Logins.** Passwords: PBKDF2 with a per-user salt plus the server-side pepper; failed logins are
  throttled per user and per address. Access tokens live 15 minutes; refresh tokens are **rotated on
  every use**, and an old refresh token coming back revokes the whole session (a stolen copy is
  useless after one refresh). "Remember me" off keeps the token in the tab only (`sessionStorage`)
  and ends idle sessions.
- **The GPU backend** accepts only short-lived, single-use run tokens signed by the control plane
  (bound to the action, the user and the job); it calls the control plane with HMAC-signed requests.
- **The browser** is protected by a strict Content Security Policy (`web/_headers`, generated by
  `scripts/csp_headers.py`): no inline script that is not hash-listed, no third-party script except
  jsDelivr (where browser-side preparation loads Pyodide from), and no framing by other sites.
- **Audit log.** Admin actions (users, roles, password resets, the model catalog, system limits),
  session deletions and password changes are recorded with who and when (**Admin → Audit log**).
  Passwords and tokens are never written to it.
- **Problems.** The GPU server keeps its recent warnings, errors and failed runs in memory for
  admins (**Admin → Problems in the last 24 hours**); nothing is sent elsewhere.

## 3. Why the refresh token is not in a cookie

An HttpOnly cookie would hide the refresh token from page scripts. Here, the site
(`*.pages.dev`) and the control plane (`*.supabase.co`) are different sites, so the cookie would be a
**third-party cookie**: Safari and Firefox block those by default and Chrome is restricting them,
which would log users out unpredictably. AgentMeter instead keeps the token out of reach of
injected scripts with the CSP, rotates it on every use with reuse detection, keeps it in the tab only
when "Remember me" is off, and ends idle sessions. Serving the control plane under the site's own
domain (a custom domain on both) would make a first-party HttpOnly cookie possible later.

## 4. Never commit or paste

`.env` files, `backend.env`, Supabase keys, the pepper and every value in the table above. The
repository's `.gitignore` excludes `.env`; keep `backend.env` outside the repository folder, and
check `git status` before every commit.
