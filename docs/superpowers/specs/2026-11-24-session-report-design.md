# Session PDF report, rebuilt (design)

Status: proposed, waiting for the owner's approval.
Mockup (approved as the front): `2026-11-24-report-mockup/` (`report.html`, `page-1..4.png`).

## Why
The current PDF (`agentmeter/session/pdf_report.py`, ReportLab) is a run of plain tables. The owner
finds it unprofessional and "AI generated", and it leaves out much of what the session pages show.
The new report should read like a professional benchmark report (Artificial Analysis style): charts
balanced with plain explanation, and **everything the web session analysis shows**, so the PDF can
stand on its own as evidence without the website.

## Goals
- A short story first (the approved 4-page front), then the full detail of every session tab.
- One chart per measure where the web has a chart, each with a "what this means" line.
- Every number read from the stored session results. A few web views are calculated in the browser
  (Capacity at a flow rate you type in, rank stability under other weight presets). These are
  ported to Python with parity tests against the web code, the way `brief.py` already mirrors
  `web/report.js`. Typed-in inputs use the web's defaults, and the report states the default used.
  (My call.)
- Older sessions lack some parts (the golden fixture has no `drivers`, for example). A missing part
  is left out with one line saying it was not recorded for this session.
- Works for 1 to 7 models, real GPU runs and demo (mock) runs.
- Made on the GPU server when the benchmark finishes, as today, so it exists when the GPU is off.

## Non-goals
- No interactive parts. Sliders, filters and the flow explorer become fixed tables and charts.
- No change to any score, rank, verdict or statistical rule. Presentation only.
- No change to how the PDF is stored or downloaded (`/api/jobs/<id>/report.pdf`, uploaded once to
  the control plane).
- Old sessions keep the PDF they already have.

## Anti-goals (a failure even if it works)
- A sentence that the data does not support. The mockup review found three (a 5% rule that is
  really 2%, a "Best" on an untested measure, a made-up reason for the score). Explanations must be
  generated by rules from the data, never by an AI model and never as fixed text that assumes a result.
- Making GPU start-up slower or more fragile.
- Em dashes, semicolons or clause colons in the report's sentences (owner's writing rule).

## Approaches considered
1. **HTML template turned into a PDF by WeasyPrint. Picked by the owner.** Same HTML/CSS
   approach as the mockup. Charts drawn as SVG by Python. No browser on the GPU machine. Tried on the
   mockup: 4 pages in about 3 s, about 85 MB installed. Cost: each web chart is redrawn in Python.
2. HTML printed by headless Chrome. Exact mockup look, but about 300 MB of Chrome on every Vast
   machine, slower and more fragile start-up.
3. Keep ReportLab and add charts. No new install, but hard to reach the look and slow to build.
Printing from the website was ruled out: the PDF must exist when the GPU is off and is uploaded as a file.

## Structure of the report
Section order follows the session tabs. Each detail part opens with one or two sentences saying
what the part answers, then charts, then tables, each chart with its "what this means" line.

**Front (about 4 pages), as in the approved mockup**
1. Header (GPU, precision, flows, date, job id), verdict headline, "In plain words" (three
   takeaways), "Which one to pick", "How to read the charts", "Keep in mind" (the session's caveats).
2. Every measure, one chart each (latency, p95, working memory, total peak memory, tokens, cost,
   energy, efficiency score), Best / Tie / not-tested tags, "Putting it together".
3. Speed against cost scatter, comparison table, where the time goes agent by agent, glossary.
4. How each number is measured, how a winner is decided, how the score works, what was held equal,
   what to do next.

**Detail parts (about 10 to 16 pages, depending on models and data)**
- **Overview**: input (file, flows, sample), flow selection rules fired, models evaluated, demo warning.
- **Ranking**: Scores (efficiency score bars and the per-criterion points), Weighting (the weights
  used), Robustness (how the order changes under other weight presets), Trade-offs (Pareto frontier
  chart), Model Guide (best model per need: fastest, shortest slow tail, cheapest, smallest memory,
  fewest tokens, most valid answers).
- **Output reliability**: usable answers per model, accuracy against reference labels when labels
  exist (per class), misclassification resource cost, IDS to LLM triage and the triage table
  (missed attacks, false escalations, analyst queue).
- **Performance**: Comparison (per attack class), Latency (distribution with p50/p95/p99, mean
  without warm-up, stability CoV, prefill against decode), Capacity, What drives it, GPU and
  throughput (output throughput, clock, temperature, slow-down flags), Statistics (Kruskal-Wallis,
  effect sizes with confidence intervals, flows needed for a clear answer).
- **Agents**: per-agent time, tokens and memory per model, stacked time bar per model, hand-off tokens.
- **Cost and energy**: cost per 1,000 flows, energy per flow and net of idle, GPU price source.
- **Recommendations**: Your limits (only when the PDF was downloaded with limits, as today), Model
  context (Hugging Face reference info), Deployment guidance and optimisation hints.
- **Data**: the prepared set (hash, sample, class mix), and a flows table limited to the flows that
  matter: wrong answers, dismissed attacks, escalations, model disagreement and the 10 slowest, up to
  60 rows. The full list stays in the CSV download, and the report says so. (My call: a full list
  could be thousands of rows.)
- **Back matter**: methodology, glossary and FAQ (from the same source text as the web's Help).

## Explanations without mistakes
- Each "what this means" line, takeaway and pick comes from a small rule in
  `agentmeter/session/report_text.py`, a function of the stored results, with a unit test per rule
  that checks wording for a win, a tie, an untested measure and a missing value.
- Tags come from the session's own comparison result: **Best** only when the session marked the
  difference as real (over the threshold and p below 0.05 where tested), **Tie** when it did not,
  an outlined **not tested** tag for measures the session does not test (p95, total peak memory,
  the score). Thresholds are read from the results, not typed into the template.
- The verdict headline is the session's own verdict text, as today.
- A missing value (no price, no power reading, demo run) shows "not measured" with the reason,
  never a zero and never a guess.
- A test greps the rendered text for em dashes, semicolons and clause colons.

## Single-model sessions
The front keeps its shape. Bars compare the model against the score's targets (5 s, 16,000 MB,
1,200 tokens) instead of another model. "Which one to pick" becomes "Is this model a fit", the
scatter is left out, and the text says a second model is needed for a comparison. (My call.)

## Many models (3 to 7)
Bars sort best first and use the app's model colours. The scatter labels every dot. Tables keep one
column per model, switching the page to landscape for 5 or more models. (My call.)

## How it is built
- `agentmeter/session/report_html.py`: builds a view model from the results (the same inputs as
  today's `build_report_pdf`), renders Jinja2 templates in `agentmeter/session/report_templates/`
  and calls WeasyPrint.
- `agentmeter/session/report_charts.py`: small SVG chart functions (bars, stacked bar, scatter,
  histogram, line over time), drawn in Python, no plotting library.
- Fonts: Inter and Inter Tight (open licence) stored in the repo, so rendering never fetches the web.
- `report_pdf_bytes` in `agentmeter/server/jobs_api.py` calls the new builder. **If WeasyPrint is
  missing or fails, it falls back to today's ReportLab report** and logs why. (My call: a run must
  never end without a PDF.)
- Install: `weasyprint` in `requirements.txt`. `vast_up.sh` installs the Pango system libraries it
  needs with apt when they are missing, the same way `vast_onstart.sh` installs tmux.

## Testing
- Unit tests for every text rule and chart function.
- Render tests on the golden session fixture (`tests/fixtures/golden_session`), a single-model
  session, a 5-model session and a demo run: page count in range, every section present, no
  "None"/"nan" in the text, every number on the front present in the results.
- Fallback test: with WeasyPrint unavailable, the ReportLab PDF is still returned.
- Page images of each fixture saved for the owner to review before release.
