    Benchmark the resource efficiency of LLMs on your network flows

    AgentMeter measures how efficiently open-source language models run a fixed 4-agent analysis task: latency, GPU memory, tokens, cost and energy — plus a check that every answer is usable. It is a measurement tool, not a threat-detection product, and it makes no security decision about your network.

    How AgentMeter works

    1. Data. Upload a CSV (CIC-IDS2017 flows, with labels) or a PCAP. AgentMeter samples the flows you ask for and keeps them as a prepared set you can reuse. The GPU server does the sampling when it is free; while it is busy with another benchmark, AgentMeter does it in the cloud instead (or, without cloud preparation, in your browser), so a new dataset never waits in the queue. Every route runs the same Python code, so the prepared flows are identical.
    2. Models. Pick one to four open models (4-bit). The wizard estimates the time and cost from earlier runs.
    3. Run. Each flow goes through the agents — by default Perceive, Reason, Decide, Act, or your own pipeline — one model at a time, on the same GPU.
    4. Read. Each session tab opens with a one-line summary; tables download as CSV, line charts and diagrams as PNG. Reference labels only check that the output is valid: AgentMeter measures efficiency.

    How to use AgentMeter

    AgentMeter measures how efficiently open LLMs run a 4-agent SOC triage pipeline on your own network flows: speed, GPU memory, tokens, cost and energy. Classifying the flows is the workload the agents perform, not what is being evaluated: the output is only checked for validity.

    1. Run a benchmark

    1. Upload. Open New Benchmark and upload a CSV of flows (CIC-IDS2017 or another CICFlowMeter export, with a Label column for the reference-label check) or a PCAP, and choose how many flows the benchmark samples. No GPU needed: the preparation service on your computer does it (if it is not running, click Start the preparation service).
    2. Preparing and your data. The data is prepared and the IDS scores every flow. Then you see what is in it, the alerts, what the IDS caught and missed (labelled CSV), a threshold to try, and the projected LLM cost. Continue when the GPU server is running.
    3. Models. Pick one to four open models. Every model runs in 4-bit NF4 on the same GPU, one at a time, so the numbers are comparable. The wizard estimates time and cost from earlier runs.
    4. Agents. Keep the default pipeline (Perceive → Reason → Decide → Act) or build your own: up to 8 agents, from the built-ins, ready-made templates or agents you write. Exactly one agent gives the answer (a label agent); each agent reads the flow and/or earlier agents' answers.
    5. Options. Tick Load test to also measure how throughput scales with 1, 2 and 4 flows in parallel, and repeat check to answer the first 10 flows twice (does the model give the same answer?).
    6. Run. The session page shows live progress. If the GPU is busy, your run is queued and starts by itself; with a Telegram chat in Settings you get a message when it finishes. You can leave the page; the run continues on the GPU server. Stop it from the same page if needed.

    No GPU connected? The app says so in the sidebar. Uploading and preparing data, the IDS results and old sessions still work; to run a benchmark, the GPU server must be running first.

    2. Read a session

    1. Start at Overview: the headline says which model is more efficient, the tiles give the main numbers, and Key findings lists what stands out.
    2. Each tab opens with a one-line summary. Sub-tabs (such as Latency or Statistics) go one level deeper.
    3. Hover or tap a chart for exact values. Tables download as CSV and charts as PNG from the buttons under each card. The full report is in Data & Exports.
    4. Add a note or tags on the Overview tab, or a short note straight from the Sessions list, so you remember why you ran it.

    3. What each tab answers

    TabThe question it answers
    OverviewWhich model is more efficient, by how much, and what should I know before trusting it?
    Model RankingHow do the models score overall (SAW), and does the order hold if I care about different things?
    Output ReliabilityDid every flow end with a usable answer, and where do answers fail (empty, cut off, not a label)? With labelled data, a reference-label check shows the output is not noise.
    PerformanceHow fast and how steady is each model, how much GPU does it use, and are the differences real or noise?
    Agent AnalysisWhich agent (by default Perceive, Reason, Decide, Act) uses the time and tokens, what each one passes on, and what did they say for a given flow?
    Cost & EnergyWhat would it cost per 1,000 flows and per day at my volume, and how much energy does it use?
    RecommendationsDoes a model fit my latency, memory and budget limits, and what should I do next?
    Data & ExportsWhere are the PDF report, the raw results and the per-flow outputs?

    Reading the charts. On GPU over the run (Cost & Energy), hover any chart to read power, utilisation and memory at that moment together with the flow and agent that were running; drag across a chart to zoom all of them, double-click to zoom out. Inspect data under a chart shows the numbers behind it, and Chart data (CSV) downloads them. The limits you enter under Recommendations are drawn as threshold lines and colour the values that break them. Compare models (on the Leaderboard) and Repeatability share a Model and Pipeline filter. In Settings, you can be alerted on Telegram when a finished run got worse than its usual range on the same setup.

    4. Sessions, Leaderboard, Repeatability and the Cost planner

    • API documentation describes every endpoint of the control plane, the GPU backend and the cloud preparation service (who may call it, its parameters and answers). The services AgentMeter calls (Hugging Face, Telegram, Vast.ai, Supabase) are described in docs/INTEGRATIONS.md.
    • Data sets are under New Benchmark › Reuse a prepared set: your analyses (each with its IDS results) and every prepared set of flows, with its size, labels, flow mix and fingerprint, the sessions that used it, and Rename / Delete / Benchmark this set.
    • GPU & Queue (click the GPU status chip in the sidebar) shows the GPU server right now: live utilisation, memory, power and temperature, the run on it with its progress, the runs waiting in order, scheduled re-runs coming up, what just finished, and where a new file would be prepared.
    • Sessions lists every run. Search by text, filter by tag, open a session, add a note, or delete a finished session (with an account).
    • Cost planner projects each model's GPU time, cost and energy for a daily number of alerts, from its latest real benchmark on that GPU. No GPU needed.
    • Leaderboard ranks and compares models, in three tabs. By setup ranks every model on each setup (the same flows, GPU and settings). Compare models lets you choose one setup and the models on it — as many as you like, from any sessions — and puts them side by side with a ranking and a bar per model; sessions on other flows, GPUs or settings are listed with the reason they are left out. Overall counts how often each model ranks first across setups.
    • Repeatability (a tab of Leaderboard) checks that the same model on the same setup gives the same result each time it runs: each model gets a verdict — Stable, Varies or Moved — after 3 runs. To collect such runs automatically, open a finished session and use Repeat on a schedule on its Overview tab. In short: Compare = different models, same setup, one moment; Repeatability = the same model, same setup, over time.

    Methodology: how every number is measured and judged

    The rules AgentMeter applies everywhere, in one place — so a result can be checked by hand.

    What is held equal (a "setup")

    Results are only compared when three things match: the prepared set (the exact flows, identified by the SHA-256 hash of the prepared files), the GPU, and the settings (4-bit NF4 quantisation, token caps, engine and the agent pipeline, identified by a settings fingerprint). Every model then answers exactly the same flows on the same hardware, so a difference belongs to the model.

    The measures

    • Latency per flow: wall-clock time from a flow entering the first agent to the last agent's answer, per model; mean, median, p95 and p99 over all flows.
    • Working VRAM: the peak GPU memory a model needs while answering, above what was already allocated (PyTorch's peak counter is reset before each agent step and read after it); the session reports the mean and the maximum over all steps. Total peak VRAM adds the loaded weights.
    • Tokens per flow: input + output tokens of all agents for one flow, from the model's own tokenizer. Hand-offs re-send earlier answers inside later prompts, so they count too.
    • Energy per flow: GPU board power sampled during the run (NVML/nvidia-smi), integrated over each model's time window and divided by its flows. The idle board power, measured for a few seconds before each model starts, is shown separately and subtracted in "net of idle".
    • Cost per 1,000 flows: mean latency per flow × the GPU's hourly price ÷ 3,600 × 1,000. Not shown when no price is set.
    • Usable answers: the share of flows whose final answer had the required format; a validity check of the output, never part of the score.

    The SAW score (efficiency)

    Simple Additive Weighting over three criteria. Each value is normalised against a fixed target, as a cost criterion: norm = min(1, target ÷ value) — latency target 5 s per flow, VRAM target 16,000 MB, token target 1,200 per flow. The score is 100 × Σ weight × norm with the weights latency 0.25, VRAM 0.20, tokens 0.15 renormalised to sum to 1 (≈ 0.42, 0.33, 0.25). Accuracy against reference labels is never weighted in: it is reported as context only. Ranking by setup uses this stored score; the Ranking tab shows how robust the order is to other weights.

    Statistics

    • Is one model better? A model wins a measure only if it is more than 2% better and, for the per-flow measures (latency, VRAM), the Kruskal-Wallis test across the models gives p < 0.05; otherwise it is a tie, shown with its p-value. Effect sizes are Cliff's delta with a bootstrap 95% confidence interval of the difference.
    • How many flows are enough? From each model's latency spread: the flows needed to detect a given difference with 80% power at the 5% level.
    • Repeatability: a series is one model on one setup over time. Stable: every run within a limit of the median of its runs — latency 10%, tokens and VRAM 5% (they barely vary by nature); one limit for all can be chosen on the page. Moved: the latest run differs from the median of the earlier runs by more than 10% and by more than three times their typical spread (1.4826 × median absolute deviation). A verdict needs at least 3 runs.
    • Compare uses each model's latest run on the setup by default. With Every run, it shows each model's mean ± 95% confidence interval (t distribution) over its runs, and calls a difference from the best model real when Welch's t-test gives p < 0.05 and the gap is over 2%.
    • GPU state: during a run the SM clock, temperature and the driver's throttle reasons are sampled with the power. A run is flagged when the GPU was slowed down (thermal, hardware or power brake) in more than 5% of samples, ran under 80% of its maximum clock, reached 85 °C, or other processes held GPU memory.
    • Warm-up: the headline mean keeps every flow; the latency table also shows the mean without the first 5 flows (model loading and cache warm-up).

    What is never done

    No number is invented: demo runs have no GPU, so they show no energy, memory or price instead of simulated ones. Stored scores never change after a session ends; re-ranking with other weights is a view only.

    5. Key terms

    Flow
    One network connection summarised as features (duration, packets, bytes, flags…). Each flow goes through the pipeline once.
    Prepared set
    The sampled, cleaned flows from one upload. Reusing it keeps two runs on exactly the same data.
    SAW score
    Simple Additive Weighting: each efficiency criterion (latency, VRAM, tokens) is scaled 0–1 against a target and combined with weights into one score out of 100.
    p95 latency
    95% of flows finished faster than this. It shows the slow tail that an analyst queue actually feels.
    VRAM
    GPU memory. Total peak includes the model weights; working is what the agent calls add on top.
    Label agent
    The one agent in a pipeline that gives the answer: an attack class from the allowed list (Decide in the default pipeline). The reliability check reads its answer.
    Hand-off tokens
    Earlier agents' output that a later agent's prompt re-sends: the overhead of splitting the work into agents.
    4-bit NF4
    The quantisation every model runs in, so a 7B model fits on one GPU and all models are measured the same way.
    Demo (mock)
    A run without a real model, to try the app. Its numbers are not measurements.

    6. Common questions

    Is AgentMeter a threat detector?

    No. Triaging the flows is the realistic SOC workload the agents perform: each flow gets a class and, from the session's policy table (not the model), a priority — Escalate, Investigate or Dismiss. AgentMeter measures what that work costs (time, GPU memory, tokens, money, energy). The answers are checked for validity and their triage (missed attacks, false escalations, the analyst queue) is shown as context in Output Reliability, so a fast but unusable pipeline is never called efficient; neither changes the efficiency score. Without labels (a PCAP) the reference-label check is skipped; everything else works.

    Why does my result say "could not be tested" or "tie"?

    With few flows, a difference can be noise. Performance → Statistics shows how many flows you need for a clear answer.

    Why are cost or energy "not measured"?

    Cost needs the GPU's hourly price: the live Vast.ai price, or AGENTMETER_GPU_USD_PER_HOUR on the GPU server. Energy needs the GPU's power reading, which some cloud GPUs do not expose. Demo runs measure neither.
